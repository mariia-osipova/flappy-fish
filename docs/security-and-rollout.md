# Защищённый рейтинг: устройство и выпуск

Код сохраняет существующий Node.js-хостинг AI Studio. Google Sheets остаётся
единственным постоянным хранилищем. Новый сервер по умолчанию запускается с
**выключенным рейтингом**; тренировка и Evolution работают без Google.

Изменение репозитория не закрывает старые Apps Script deployments и не меняет
опубликованный сайт. До выполнения шагов владельца ниже прежний публичный
обработчик по своему старому адресу остаётся опасным.

## Локальный запуск

Нужен Node.js22 или новее. Для воспроизводимой установки используется `bun.lock`:

```sh
npm exec --yes --package=bun -- bun install --frozen-lockfile
npm run build
npm test
npm start
```

Открыть `http://localhost:3000`. Без секретов кнопка рейтинговой игры сообщает о
недоступности сервера; кнопка **Practice (unranked)** остаётся доступна.

Для локального сервера с собственным staging-хранилищем скопировать
`.env.example` в `.env`, заполнить секреты и запустить `npm run dev`.
`.env` исключён из Git. В production значения задаются в AI Studio Secrets,
а не через клиентскую сборку или `config.js`.

Для рейтинговой игры нужен HTTPS: не отключайте `Secure` у cookie ради
локальной отладки. Используйте staging-домен; браузерные тесты поднимают
собственный временный HTTPS-сервер. Обычный HTTP-запуск подходит для тренировок.

| Переменная Node | Назначение |
| --- | --- |
| `RANKED_ENABLED` | `false` до проверки и миграции; `true` включает рейтинговые записи |
| `APP_ENV` | `production`; только на отдельном тестовом сервере — `staging` |
| `APPS_SCRIPT_URL` | HTTPS `/exec` защищённого Apps Script; только на сервере |
| `SESSION_HMAC_KEY` | Секрет подписи анонимной cookie |
| `STATE_HMAC_KEY` | Другой секрет подписи игровых снимков |
| `GATEWAY_HMAC_KEY` | Третий секрет; такой же только в Script Properties шлюза |
| `VERIFIER_WORKERS` / `VERIFIER_QUEUE` | По умолчанию2 worker и10 ожидающих блоков |
| `GATEWAY_TIMEOUT_MS` | По умолчанию10000; неизвестный результат не считается сохранённым |

Каждый секрет генерируется отдельно из минимум32 случайных байт, например
`openssl rand -hex 32`. Короткие и совпадающие ключи отключают рейтинг.
Не менять ключи при обычном перезапуске или создании нового экземпляра Node:
иначе ранее выданные cookie/снимки перестанут работать.

## Что проверяется

`src/shared/game-core.js` исполняется и браузером, и Node worker. Одна версия
фиксирует физику120Hz, Mulberry32, альфа-маску рыбы, таблицу поворотов,
порядок препятствий/очков/смерти. Интервал препятствий сохранён как181 шаг:
так работал прежний таймер с float-сложением. Ввод — один байт на шаг:
`left=1`, `right=2`, `flap=4`; одновременно нажатые стрелки поддерживаются.

Node принимает максимум1200 шагов за запрос и сам вычисляет результат.
Время, координаты, seed, очки и bestScore из дополнительных полей браузера
отклоняются. Нельзя продолжить replay после вычисленной смерти. Пауза может
содержать пустой блок, обычный checkpoint — нет. Тело запроса ограничено8KiB,
декодированный подписанный снимок —4KiB, проверка —250ms в ограниченном
пуле workers. Превышение очереди/лимита возвращает503/429.

Счётчик шагов сравнивается с активным временем по часам сервера, с допуском1s.
При паузе время не добавляется; при истечении lease учитывается только время
до его конца. Ранее накопленное активное время сохраняется, чтобы можно было
дослать записанный офлайн-хвост после получения нового места.

## API и сохранение

| API | Тело/результат |
| --- | --- |
| `POST /api/session` | `{}`; подписанная `__Host-flappy_session`, HttpOnly/Secure/SameSite=Lax |
| `POST /api/games` | `{name,requestId}`; seed и подписанный начальный checkpoint |
| `POST /api/games/:id/checkpoints` | `{requestId,checkpointToken,seq,inputsBase64,pause}`; `seq=предыдущий+1` |
| `POST /api/games/:id/resume` | `{requestId,checkpointToken}`; CAS старого снимка и новое поколение lease |
| `GET /api/games/:id` | Только собственная партия: подтверждённый снимок и последний requestId |
| `GET /api/scores?name=...` | top100, точный рекорд ника даже вне top100, происхождение результата |

Старый `POST /api/scores` возвращает410. JSONP отсутствует. Публичная выдача рейтинга
не содержит адреса Google, ownerId, cookie, gateway secret или внутреннего
индекса всех игроков. Проверки доступа основаны на подписи и владельце
партии; CORS и IP не используются как доказательство личности.

GAS получает HMAC-SHA256 POST, который связывает действие, точное содержимое,
requestId и timestamp. Подпись проверяется **до SpreadsheetApp**. Один Games
JSON-cell содержит всю авторитетную запись партии, включая последний ответ и
финальные очки. Под ScriptLock проверяются seq/hash/leaseEpoch; до unlock
выполняется flush. Идентичный повтор последней операции возвращает сохранённый
результат, другая ветка конфликтует. Node подписывает новый снимок только после
подтверждения GAS. Ответ потерян — статус записи неизвестен, повторяем тот же
requestId или сверяем GET. Перезапуск Node не удаляет партии.

При возобновлении leaseEpoch увеличивается. Старый запрос resume тоже проверяет
CAS и не может оживить партию после более поздней паузы. Общего таймера окончания
партии нет: размер снимка и записи не растёт с длительностью игры.

## Клиент, места и рейтинг

- По умолчанию5 активных рейтинговых партий глобально,1 на анонимную сессию.
  Лимит задаётся `MAX_RANKED_GAMES` в Script Properties. Это не лимит посетителей.
- Через120s без подтверждённого прогресса место свободно. Партия остаётся в
  Games. Пауза сохраняет хвост и освобождает место; resume заново проверяет лимит.
- IndexedDB хранит неподтверждённый ввод и стабильные requestId. Запросы идут
  последовательно. Буфер30s автоматически останавливает физику при заполнении.
  После сбоя клиент сверяет последний подтверждённый блок; чужую ветку не
  переписывает. Web Lock не позволяет двум вкладкам перезаписывать одну очередь.
- Нет места/сервер недоступен — предлагается явно выбрать тренировку.
  Уже сыгранная тренировка никогда не превращается в рейтинговую партию.
  Evolution также не отправляет результаты.
- localStorage помнит только ник. Официальные рекорды берутся с сервера;
  старые клиентские score-ключи больше не читаются.
- Рекорд — максимум исторического и завершённых проверенных результатов по
  нормализованному нику. При равенстве выигрывает проверенный. История помечена
  `legacy` / «без серверной проверки». Импорт не делает её достоверной.
- Сервер кэширует агрегированные рекорды30s общим индексом; поиск разных ников
  использует тот же кэш. Ответ API содержит только top100 и искомого игрока.
  Кэш никогда не определяет владельца, текущее состояние или свободные места.

Ники не принадлежат аккаунтам: регистрации нет, один ник могут использовать
разные люди. Удаление cookie лишает браузер доступа к старой партии.
Корректно играющий бот может пройти проверку и занимать место. Эти ограничения
сознательно не заменяются секретом, спрятанным в JavaScript.

## Проверки

```sh
npm test
npx playwright install chromium webkit
npm run test:browser
npm run build
```

Браузерному тесту с настоящей Secure-cookie также нужен `openssl` в PATH:
он создаёт временный HTTPS-сертификат только для локального тестового сервера.
Production-настройки cookie не ослабляются.

Node-тесты включают реальный `Code.gs` в изолированной VM с поддельным
SpreadsheetApp и внедрением сбоев. Проверяются подписи, чужие сессии, oversized
input, смерть, скорость, повтор/потеря ответа, рестарт, конкуренция, stale epoch,
паузы, миграция, provenance и клиентский outbox. Браузерные тесты сравнивают
точный JSON эталонных партий в Chromium/WebKit/Node, клавиатуру/касание, коллизии,
паузу и независимость рейтинга от localStorage. Тесты не обращаются к Google.

## Нагрузочный тест на отдельной таблице

1. Подготовить отдельные таблицу, GAS deployment и Node staging. Загрузить
   репрезентативную накопленную историю через штатную миграцию. Указать объём
   Games и число уникальных ников в отчёте: сканирование истории — ограничение
   этого решения на Sheets.
2. Вручную проверить, что `SPREADSHEET_ID`/`APPS_SCRIPT_URL` указывают именно на
   тестовые ресурсы. Установить `APP_ENV=staging`, включить рейтинг только там.
3. Запустить генератор:

```sh
LOAD_TARGET_URL=https://YOUR-STAGING-HOST \
LOAD_CONFIRM=STAGING_ONLY \
npm run test:load
```

По умолчанию500 HTTP-посетителей загружают игровые ассеты и опрашивают рейтинг,
а5 проверяемых ботов отправляют блоки10s на протяжении5min. Это модель HTTP
нагрузки, не500 запущенных графических браузеров. Скрипт отказывается работать
с известными production-доменами и сервером без staging-флага, но флаг не
доказывает изоляцию таблицы — это проверяет владелец. Завершение теста оставляет
незавершённые игры на паузе, не удаляя историю.

Критерий: p95 подтверждения блока≤5s, без ошибок штатных запросов, без ошибок
квот Google. После запуска проверить журнал Apps Script и квоты отдельно:
HTTP-успех сам по себе не доказывает запас квот. Записать latency/retries,
объём истории, регион/настройки Node и фактические показатели Google.

Локальные mock-тесты не заменяют этот замер. Начальные5 мест ещё не являются
доказанной производительностью; повышение требует нового теста.
[Квоты Apps Script](https://developers.google.com/apps-script/guides/services/quotas).

## Выпуск владельцем

1. Настроить и проверить staging по
   [инструкции Apps Script](../src/google-apps-script/README.md). Пройти полный
   путь start→checkpoint→pause/resume→death→rank без записи в рабочую таблицу.
2. На время миграции остановить приём результатов старой версией. Закрыть
   **все** публичные writer deployments, включая резервные адреса, GET-save,
   старые версии `/exec`, другие script projects и возможные прямые права
   редактирования таблицы. Простого удаления URL из нового JS недостаточно.
3. Снять отдельный snapshot исходной истории. `initializeStorage()` создаёт
   служебные листы, `migrateLegacyScores()` повторяемо заполняет Legacy.
   Исходный Scores остаётся нетронутым; проверить отчёт invalidRows/warnings.
   Пользовательский текст в Games/Legacy хранится внутри JSON, не формулами.
4. Развернуть защищённый Apps Script, обновить сервер и frontend, настроить
   три отдельных секрета в AI Studio Secrets. `RANKED_ENABLED=false` сохраняет
   безопасное окно проверки; после контрольной записи включить рейтинг.
5. Проверить production-cookie по HTTPS, отказ неподписанного GAS запроса,
   невозможность старого GET-save, сохранение и появление проверенного рекорда.
   Не проверять запрещённую запись тестовым поддельным рекордом в рабочую таблицу.

В обычном rollout всех экземпляров Node должны совпадать ключи и версия ядра.
При будущем изменении правил сохранить verifier старой версии до завершения
старых партий либо явно объявить их несовместимость; новый verifier не должен
интерпретировать старый снимок по новым правилам.

## Наблюдение и откат

Node пишет структурированные `api_request` события: тип операции, HTTP-status,
latency и код ошибки, без тела, ников, идентификаторов или секретов. Следить за
`storage_unavailable`, `verification_timeout`, `verification_busy`, `conflict`,
`ranked_full`,429, временем checkpoint. В Apps Script наблюдать lock/quota
ошибки и активные Games (`status=active`, `leaseUntil>now`). Проверку занятости
принимать только из реального хранилища, не из leaderboard-кэша.

При инциденте отключить `RANKED_ENABLED`, оставив тренировку доступной.
Неподтверждённые хвосты остаются у браузеров; после исправления восстановить их
через GET/retry. **Не возвращать старый незащищённый writer при откате.**
Публичный Apps Script URL, даже с HMAC, не защищён от расходования квот запросами;
при целенаправленной нагрузке потребуется дополнительная защита инфраструктуры.
